Спроектируйте и частично реализуйте однопоточную очередь AsyncQueue<T>, с которой можно работать из корутин:

```
co_await queue.push(value);
auto x = co_await queue.pop();
```

Очередь имеет ограниченную ёмкость. Если очередь заполнена, push приостанавливает корутину. Если очередь пуста, pop приостанавливает корутину. При появлении места или элемента соответствующая корутина возобновляется. Можно считать, что всё происходит в одном потоке и многопоточная синхронизация не нужна.
---
Спроектируйте и частично реализуйте однопоточный AsyncMutex, предназначенный для корутин:

```
auto guard = co_await mutex.lock();
```

Если mutex свободен, корутина продолжает исполнение и получает guard. Если mutex занят, корутина приостанавливается. При уничтожении guard mutex освобождается и возобновляет следующую ожидающую корутину.

Спроектируйте и частично реализуйте шаблонный класс CowBuffer<T>. При копировании несколько объектов разделяют один буфер. При неконстантном доступе буфер отделяется, если он разделён. Счётчик ссылок должен быть атомарным, чтобы разные копии можно было уничтожать из разных потоков. Модификация одного и того же объекта из нескольких потоков не обязана быть thread-safe. Нужно использовать allocator-aware хранение.

Элементы, добавленные во время построения snapshot-а, могут не попасть в текущий snapshot, но не должны быть потеряны.

Спроектируйте и частично реализуйте Versioned<T>.

Один поток публикует новые версии объекта. Много потоков получают read-only snapshot текущей версии и работают с ним без блокировки writer-а.

```
auto snapshot = object.snapshot();
object.update([](T& value) { ... });
```

При этом snapshot должен оставаться валидным, даже если после этого опубликована новая версия, а читатель не должен видеть частично обновлённое состояние.
---
Спроектируйте и частично реализуйте lock-free очередь задач для work stealing.
В такой очереди:
Владелец очереди может делать push и pop с одного конца.
Другие потоки могут делать steal с другого конца.
Обратите внимание: вам нужно явно разобрать гонку между pop последнего элемента и steal.
---
Спроектируйте и частично реализуйте сборщик статистики. Под статистикой понимается набор счётчиков, который часто увеличивают много потоков, а один поток периодически читает их агрегированное состояние. Нужно минимизировать false sharing.

Спроектируйте и частично реализуйте структуру данных LogBuffer<T> для сбора событий.

Много потоков-производителей могут добавлять события:

```
log.push(event);
```

Один поток-потребитель периодически забирает накопленные события пачкой:

```
auto batch = log.drain();
```

При этом push не должен брать общий mutex, drain вызывается только одним consumer-потоком, а все события, успешно опубликованные до некоторой точки drain, должны попасть либо в текущую пачку, либо в следующую, но не должны быть потеряны. Обратите внимание, что каждое событие должно быть возвращено ровно один раз.

Наличие только одного consumer позволяет вам в этой задаче сделать destructive drain: одним атомарным действием отрезать список/пачку и дальше единолично её разбирать (что невозможно будь консьюмеров много). Используйте именно эту стратегию. Обсудите (не пишите код) что бы вы делали в случае многих консьюмеров.

(2) для достижимой вершины v значение dist[v] равно минимальному числу рёбер от start до v;

Ваш алгоритм должен идти по уровням BFS и распределять построение границы между потоками, каждый из которых обрабатывает свой участок границы. Продумайте как вы будете фиксировать посещённые вершины.
